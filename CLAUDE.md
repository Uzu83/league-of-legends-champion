## Project

LOL キャラタイプ診断 (League of Legends Character Type Diagnosis) — a stateless, mobile-first Next.js web service that maps a user's personality / play-style answers to the closest LoL champion via vector distance.

The headline differentiator is the **two-entry design**: users pick either ストーリー入り口 (worldview / values / relations) or ゲーム性能入り口 (role / archetype / skill traits). Each entry asks 10 Likert questions and ranks all champions by Euclidean distance to the user's answer vector. The result page cross-promotes the *other* entry.

This is the LOL counterpart to the **サイリウムカラー診断 (penlightcolor)** project — the spec mandates inheriting that project's stack and stateless-content-addressed-URL DNA.

Source spec: Notion page `LOLキャラタイプ診断` (id `3541ef84-88d5-8181-9de6-ede4a562d202`).

## Architecture

### Data flow

1. User picks an entry on `/` → `/q/[type]` (`type ∈ {story, game}`).
2. `app/q/[type]/quiz-client.tsx` renders 10 questions from `lib/questions.ts`. Answers go into a Zustand store persisted to `sessionStorage` (`lib/store.ts`).
3. On submit, answers are encoded into a hash (e.g. `s5443215543`) by `lib/encoding.ts` and the user is routed to `/result/[hash]`.
4. `/result/[hash]` decodes the hash → calls `topMatches()` from `lib/scoring.ts` → renders best match + 3 close alternatives + cross-entry CTA.
5. `/api/og?hash=…` (Edge runtime) generates the Twitter Card / OGP image via `next/og`.

The hash *is* the data. There is no backend, no DB, no user state across sessions. Same hash → same result, always.

### Scoring math

`lib/scoring.ts`:

- Each question has a sparse weight map over named dims (e.g. `{ honor: 0.8, organization: 0.9 }`).
- A Likert answer `a ∈ {1..5}` is normalized to `(a-3)/2 ∈ [-1,1]` and added (weighted) to the user vector.
- Each champion has a vector in `[0,1]^D` per entry; for distance we map it to bipolar `[-1,1]` via `2v − 1`, then take Euclidean distance.
- `D = 15` for story (10 values + 5 relations), `D = 9` for game (range / skillBased / damageStyle / durability / damage / cc / mobility / difficulty / scaling). Dim names live in `lib/types.ts`.
- Story and game share a single generic `buildUserVector` / `distance` implementation parameterized by a `DimSpec`.

If you add or rename a dim, update **all four**: `STORY_DIMS`/`GAME_DIMS` constants, the locale label maps in `lib/i18n.ts` (both ja and en), every champion's `storyVec`/`gameVec`, and the question weight maps.

### Champion data

`lib/champions.ts` is fully populated with all 172 champions (172 entries auto-generated by `scripts/fetch-champions.mjs` from DDragon, with hand-crafted overrides for ~30 seed champions). The data shape is `Champion` from `lib/types.ts`; the `s({...})` / `g({...})` helpers fill missing dims with 0 so each entry stays readable.

`name` / `title` carry the English values from DDragon `en_US`; `nameJa` / `titleJa` carry the Japanese values. The fetch script merges both DDragon files. Re-run with `node scripts/fetch-champions.mjs` whenever DDragon ships a new patch — bump `VERSION` in the script first.

`ddragonId` matches the DDragon API casing (e.g. `JarvanIV`, `MissFortune`, `Khazix`). Portraits resolve via `championPortrait(ddragonId)` against `DDRAGON_VERSION`.

EN blurbs are **synthesized** at render time from `name + title + region + archetypes` via `championBlurb()` in `lib/i18n.ts`. We deliberately do not hand-translate 172 JA blurbs — JA mode shows the curated DDragon JA text, EN mode shows the synthesized one-liner.

### Routes

All page routes resolve the active locale on every request, so they render dynamically rather than as build-time SSG. The cookie + Accept-Language read forces this — accept it, don't fight it.

- `/` — two-entry home (locale-aware, JSON-LD Quiz)
- `/q/story`, `/q/game` — quiz client (server resolves locale, passes it to client)
- `/result/[hash]` — decodes hash; bad hash → 404
- `/champions` — list with ItemList JSON-LD
- `/champions/[id]` — detail with Person JSON-LD
- `/compare` — cross-entry comparison (client-only, reads sessionStorage)
- `/api/og?hash=...&lang=ja|en` — Edge runtime, locale-aware OGP
- `/sitemap.xml`, `/robots.txt`, `/manifest.webmanifest`, `/icon`, `/apple-icon` — SEO/PWA

### `next/og` gotcha

Every `<div>` with more than one child *must* have an explicit `display: flex | contents | none` in its inline style. `flexDirection` alone is not enough. If you see "failed to pipe response" with that exact message, you forgot a `display`.

## Conventions

- **Tailwind v4** via `@tailwindcss/postcss` (PostCSS plugin), not the legacy CLI. Theme tokens are defined in `app/globals.css` under `@theme {}` and consumed via arbitrary-value syntax like `text-(--color-accent)`.
- **TypeScript strict** with `noUncheckedIndexedAccess` — array/record access yields `T | undefined`. Use `array[0]!` or `array[i] ?? fallback`.
- **i18n is wired (ja / en)**. All user-facing strings live in `lib/i18n.ts` under both locales. New copy must be added to **both** locales — never inline a string in JSX. Server components resolve the active locale via `getLocale()` from `lib/i18n-server.ts` (cookie `NEXT_LOCALE` > Accept-Language > `ja`). Client components receive the locale as a prop from their server parent.
- **Zustand store is `"use client"`** and uses sessionStorage (not localStorage) — diagnoses don't persist across browser restarts on purpose.
- **No backend.** If a feature needs persistence, it should be encoded in the URL or dropped.

## Hard Constraints (excerpt — full version in spec)

- Generic LoL lore can include "対立 / 復讐 / 死 / 戦争" because those are core to LoL fiction; do **not** prescribe them onto the *user* ("あなたは復讐に生きるべき" is out). Same restraint applies to EN copy.
- 政治 / 宗教 / 差別 の現実世界マッピングは禁止。摂食障害・自傷の言及も禁止。
- Vocabulary: avoid `Go`/`Golang`/`REST API` — use `endpoint` or `API route`.
- 曜日表示は日曜始まり。
